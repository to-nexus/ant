## 1. Overview

### Purpose

- Evaluate game-art Design Job output quality
- Verify the game-art bundle faithfully derives from the game PRD (concept / coreloop / content scope) and, when present, the Figma / concept-art source
- Derive improvement points for the Ant program (prompts / system)

### Scope

- **Input**: game PRD (`plan/prd.md` — concept, coreloop `CL-`, MDA `MC-`, content scope `EN-`/`LV-`, input & perspective), game system-design, optional Figma / concept-art references
- **Output**: game-art-spec.json, game-art-tokens.json, game-art-assets.json

### Core Principle

> **"Does the game-art bundle realize the PRD's aesthetic and content commitments, without inventing scope the PRD did not commit?"**

The game PRD is the SSOT. Every asset category and token must trace to a PRD commitment (an `EN-`/`LV-` entity, an `MC-` mechanic's feedback, the §4 MDA Aesthetic, or the §9 viewport/perspective). Asset categories with no PRD anchor are over-production; missing categories for committed entities are gaps.

## 3. Evaluation Process

### 🚨 CRITICAL: Evidence-Based Evaluation Principle

> **"NO SCORE WITHOUT EVIDENCE"**
>
> Complete the PRD-anchor trace BEFORE assigning any scores. Scores without documented evidence are INVALID.

### Step 1: PRD Commitment Log (MANDATORY FIRST)

Before reading the game-art documents, read the PRD and record its aesthetic and content commitments:

```markdown
## PRD Commitment Log

- **§4 MDA Aesthetic**: [intended feeling in palette/silhouette/lighting/motion-tone words, or "not committed"]
- **§8 Content Scope**: [list every EN-XXX entity and LV-XXX level with its integer count]
- **§9 Input & Perspective**: [viewpoint (2D side / 2D top / 3D), orientation policy, viewport target]
- **§4 Mechanics (MC-XXX)**: [mechanics whose feedback needs visual/motion treatment]
- **§6 Reward & Feedback (RW-XXX)**: [reward feedback visuals, when present]
- **External asset citations**: [any concept/sprite/sound/figma citation the PRD attached to an entity]
```

If a source (Figma / concept art) is in the RAC, also observe it and record what it covers.

### Step 2: Game-Art Document Collection

```markdown
Read the following files:
1. `visual/game-art/ant/game-art-spec.json`   - categories, HUD/menu/dialog
2. `visual/game-art/ant/game-art-tokens.json`  - palette / silhouette / lighting / motion-tone + HUD CSS tokens
3. `visual/game-art/ant/game-art-assets.json`  - inline + external asset mapping
4. `plan/prd.md`                               - PRD for anchor verification
```

### Step 3: Evidence-Based Comparison (DETAILED)

For EACH `EN-`/`LV-` entity in the PRD §8 catalog, create an anchor record:

```markdown
| PRD anchor | game-art-spec category | Token derivation | Asset kind | Match |
|------------|------------------------|------------------|------------|-------|
| EN-Hero    | entities/hero          | palette + silhouette present | inline / external | ✅/❌ |
```

### Step 4: Score Assignment (ONLY AFTER Steps 1-3)

**Scoring Criteria:**

- ⭐⭐⭐⭐⭐: every PRD commitment realized, no over-production, tokens coherent
- ⭐⭐⭐⭐☆: 90%+ anchored, minor gaps only
- ⭐⭐⭐☆☆: 70-89%, some committed entities missing or unanchored categories present
- ⭐⭐☆☆☆: 50-69%, multiple critical gaps
- ⭐☆☆☆☆: <50%, bundle does not derive from the PRD

**Scoring Discipline — evaluate strictly:**
- **When in doubt, score lower.** Uncertainty about whether a category traces to the PRD is a mismatch signal.
- **Do not award points for category existence.** A category that exists but has no PRD anchor is over-production, not partial credit.
- **Treat every mismatch as a Code Job failure** — each unanchored category or missing token propagates into generated game code.

## 4. Analysis Perspectives

### 4.1 PRD Anchor Fidelity (Highest Priority)

| Item | Check Point |
|------|-------------|
| **Entity coverage** | Every §8 `EN-XXX` entity has a spec category; counts match the PRD's integers |
| **Level coverage** | Every §8 `LV-XXX` level is represented |
| **No over-production** | No asset category exists without a PRD anchor (`EN-`/`LV-`/`MC-`/`RW-`/§4 Aesthetic) |
| **Perspective consistency** | §9 viewpoint / orientation / viewport reflected in spec (camera scheme, aspect) |

### 4.2 Token Accuracy

| Item | Check Point |
|------|-------------|
| Palette | Colors derive from §4 MDA Aesthetic (or `gameArtTier.concept` when the PRD defers) |
| Silhouette | Shape language committed and consistent across entities |
| Lighting | Lighting tone present and coherent with the aesthetic |
| Motion-tone | Sprite tween / particle / projectile motion tone defined (engine-internal, NOT HUD page-transition motion) |
| HUD tokens | Spacing / typography / radius / focus-ring CSS tokens present for menu/score/dialog surfaces |

### 4.3 Asset Mapping Accuracy

| Item | Check Point |
|------|-------------|
| Inline vs external | `kind: 'inline'` stays within the css-only ceiling (single-color shapes, ≤5 svg primitives, OscillatorNode configs); production-quality assets are `kind: 'external'` under `assets/game/` |
| External `src` path | External items point under `assets/game/` (never `assets/service/`) |
| Citation honored | Entities the PRD cited an external asset for use that asset as `external` `src` |
| Usage clarity | Each asset's category / usage is unambiguous |

### 4.4 Spec Completeness

| Item | Check Point |
|------|-------------|
| In-canvas categories | Entities, projectiles, particles, backgrounds covered |
| HUD / menu / dialog | Present as spec categories alongside in-canvas categories |
| Content accuracy | Category names / counts trace to the PRD verbatim (no shadow IDs) |

## 5. Evaluation Checklist

### 5.1 PRD Anchor Fidelity
- Does every `EN-`/`LV-` entity in PRD §8 have a matching spec category?
- Are there any spec categories with NO PRD anchor? (over-production)
- Is the §9 perspective / orientation / viewport reflected?

### 5.2 Token Quality
- Are palette / silhouette / lighting / motion-tone tokens all present and coherent?
- Are HUD CSS tokens (spacing / typography / radius / focus-ring) defined for React overlay surfaces?
- Is token naming semantic (`palette.enemy.primary`, not raw hex keys)?

### 5.3 Asset Mapping Quality
- Do inline payloads stay within the css-only ceiling? (svg ≤5 primitives, css <100 chars)
- Do external items resolve under `assets/game/`?
- Are PRD external-asset citations honored per entity?

### 5.4 Spec Quality
- Are in-canvas AND HUD/menu/dialog categories both covered?
- Do all identifiers trace to PRD `EN-`/`LV-`/`MC-`/`RW-` (no invented shadow IDs)?

## 7. Usage

**🚨 MANDATORY EVALUATION ORDER:**

1. **READ THE PRD FIRST** — record §4 Aesthetic, §8 `EN-`/`LV-` catalog, §9 perspective in the PRD Commitment Log.
2. **RECORD COMMITMENTS** before reading any game-art document.
3. **THEN READ game-art documents** — find the category / token / asset for each commitment.
4. **CREATE THE ANCHOR TABLE** — column 1: PRD anchor; column 2: game-art value (verify the field EXISTS); column 3: Match / mismatch / MISSING.
5. **ONLY THEN ASSIGN SCORES** — every score references anchor-table evidence.

**Anti-Patterns to AVOID:**
- ❌ Scoring first, evidence later
- ❌ Awarding credit for a category that has no PRD anchor
- ❌ Treating a `kind: 'inline'` payload over the css-only ceiling as acceptable
- ❌ Flagging a missing document as a failure — note it was not available and move on
