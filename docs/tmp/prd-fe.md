# PRD: GoShort Dashboard

---

## 1. 요약

URL 단축 서비스(GoShort)의 관리 대시보드 웹 애플리케이션. 단축 URL 생성, 목록 조회, 상세 정보 확인, 삭제 및 클릭 통계 시각화 기능을 제공한다.

---

## 2. 문제 / 목표

### 목표
- 관리자가 단축 URL을 생성하고 기존 URL 목록을 페이지네이션으로 탐색할 수 있는 웹 인터페이스를 제공한다.
- 개별 단축 URL의 상세 정보와 클릭 통계를 한 화면에서 확인할 수 있도록 한다.
- 불필요하거나 만료된 단축 URL을 대시보드에서 직접 삭제할 수 있도록 한다.

### 비목표 (Non-Goals)
- 리다이렉트 서비스 자체의 구현 (별도 백엔드 서비스로 이미 존재)
- 사용자 회원가입/로그인 시스템 (API Key 인증으로 대체)
- 실시간 클릭 이벤트 스트리밍 또는 WebSocket 기반 업데이트
- 대시보드의 모바일 네이티브 앱 제공
- URL 리다이렉트 규칙 편집 (원본 URL 수정 등)
- 팀/조직 단위 다중 사용자 관리

---

## 3. 사용자 시나리오

### 시나리오 1 — 단축 URL 생성
1. 관리자가 대시보드에 접속한다.
2. URL 생성 폼에서 원본 URL을 입력한다. 선택적으로 커스텀 단축 코드를 지정할 수 있다.
3. 생성 버튼을 클릭하면, 서버에서 단축 URL이 생성된다.
4. 생성된 단축 URL(전체 주소)이 화면에 표시되어 바로 복사하여 사용할 수 있다.

### 시나리오 2 — URL 목록 탐색
1. 관리자가 대시보드 메인 화면에 접속한다.
2. 등록된 단축 URL 목록이 페이지네이션과 함께 표시된다.
3. 각 항목에는 단축 코드, 원본 URL, 단축 URL, 클릭 수, 생성 일시가 표시된다.
4. 페이지를 이동하며 전체 URL 목록을 탐색한다.

### 시나리오 3 — 상세 정보 및 클릭 통계 확인
1. URL 목록에서 특정 항목을 선택한다.
2. 해당 URL의 상세 정보(코드, 원본 URL, 단축 URL, 생성 일시)가 표시된다.
3. 동시에 리다이렉트 서비스로부터 가져온 클릭 통계(총 클릭 수, 마지막 접근 시각)가 함께 표시된다.

### 시나리오 4 — 단축 URL 삭제
1. URL 상세 화면에서 삭제 버튼을 클릭한다.
2. 삭제가 완료되면 URL 목록 화면으로 돌아가며, 해당 항목은 목록에서 제거된다.

## 4. 기능 요구사항

### 4.1 URL 생성

- **FR-01**: 원본 URL 입력 필드와 선택적 커스텀 코드 입력 필드를 포함하는 생성 폼을 제공한다.
- **FR-02**: 원본 URL의 형식을 클라이언트 측에서 사전 검증한 후 서버로 제출한다.
- **FR-03**: 생성 성공 시 반환된 단축 URL(코드, 원본 URL, 단축 URL 전체 주소, 생성 일시)을 사용자에게 표시한다.
- **FR-04**: 생성 실패 시 에러 유형(유효하지 않은 URL, 유효하지 않은 코드, 코드 충돌)에 따라 해당 입력 필드에 에러 메시지를 표시한다.

### 4.2 URL 목록 조회

- **FR-05**: 등록된 단축 URL을 페이지네이션으로 조회하여 표시한다.
- **FR-06**: 각 목록 항목에 단축 코드, 원본 URL, 단축 URL, 클릭 수, 생성 일시를 표시한다.
- **FR-07**: 페이지 번호와 페이지당 항목 수를 조정할 수 있으며, 기본값은 page=1, limit=20으로 한다.
- **FR-08**: 서버에서 반환된 전체 URL 수(total)를 기반으로 페이지네이션 컨트롤을 렌더링한다.

### 4.3 URL 상세 및 클릭 통계

- **FR-09**: 개별 URL의 상세 정보(코드, 원본 URL, 단축 URL, 클릭 수, 생성 일시)를 표시한다.
- **FR-10**: 동일 화면에서 리다이렉트 서비스의 클릭 통계(총 클릭 수, 마지막 접근 시각)를 함께 표시한다.
- **FR-11**: 상세 화면에서 삭제 기능에 접근할 수 있다.

### 4.4 URL 삭제

- **FR-12**: URL 상세 화면에서 삭제를 실행할 수 있다.
- **FR-13**: 삭제 성공 시 목록 화면으로 자동 이동하며, 해당 항목이 캐시에서 제거된다.
- **FR-14**: 존재하지 않는 URL 삭제 시도 시 적절한 에러 메시지를 표시한다.

### 4.5 인증 및 에러 처리

- **FR-15**: 모든 API 요청에 `X-API-Key` 헤더를 자동으로 포함한다. API Key는 애플리케이션 설정으로 관리한다.
- **FR-16**: API Key가 누락되거나 유효하지 않을 경우 전역 인증 에러 안내를 표시한다.
- **FR-17**: 서버 에러(500) 발생 시 일반적인 에러 메시지와 함께 재시도 옵션을 제공한다.

---

## 5. 비기능 요구사항

### 성능
- **NFR-01**: URL 목록 화면의 초기 로드는 2초 이내에 완료되어야 한다.
- **NFR-02**: 동일한 페이지/조건의 반복 요청은 캐싱하여 불필요한 네트워크 요청을 방지한다.
- **NFR-03**: 동시에 발생하는 동일 요청은 중복 제거(deduplication)하여 단일 요청으로 처리한다.

### 사용성
- **NFR-04**: 에러 응답의 코드(INVALID_URL, INVALID_CODE, CODE_CONFLICT 등)를 사용자가 이해할 수 있는 메시지로 변환하여 표시한다.
- **NFR-05**: 필드 수준 검증 에러(4xx)와 시스템 에러(5xx)를 구분하여 피드백한다.

### 보안
- **NFR-06**: API Key는 클라이언트 코드에 하드코딩하지 않고 환경 설정을 통해 주입한다.

## 6. 제약사항 및 리스크

| 구분 | 내용 |
|------|------|
| **API 의존** | 백엔드 API 서비스(포트 8080)와 리다이렉트 서비스(포트 8081) 두 개의 별도 서비스에 의존한다. 각 서비스의 가용성에 따라 기능이 제한될 수 있다. |
| **서비스 분리** | URL 관리 API와 클릭 통계 API가 서로 다른 서비스에서 제공되므로, 상세 화면에서 두 서비스의 응답을 조합해야 한다. |
| **인증 비대칭** | API 서비스는 `X-API-Key` 인증이 필요하지만, 리다이렉트 서비스의 통계 엔드포인트는 인증이 불필요하다. HTTP 클라이언트가 이를 구분하여 처리해야 한다. |
| **에러 포맷 의존** | 모든 에러 응답이 `{ error: { code, message } }` 형식을 따른다고 가정한다. 백엔드의 에러 포맷 변경 시 프론트엔드의 에러 처리 로직 수정이 필요하다. |

## 7. 기술 고려사항

### API 연동

이 대시보드는 두 개의 백엔드 서비스와 통신한다:

| 서비스 | 포트 | 사용 엔드포인트 | 인증 |
|--------|------|-----------------|------|
| api | 8080 | `POST /api/urls`, `GET /api/urls`, `GET /api/urls/:code`, `DELETE /api/urls/:code` | `X-API-Key` 헤더 |
| redirect | 8081 | `GET /api/stats/:code` | 없음 |

### 데이터 흐름
- URL 생성/삭제 후 목록 캐시를 무효화(invalidation)하여 최신 데이터를 반영한다.
- URL 상세 화면은 api 서비스의 URL 정보와 redirect 서비스의 통계 데이터를 조합하여 표시한다.

### API 계약 참조
- 전체 API 명세는 `api-contract.md`에 정의되어 있다.
- §3.1: URL 관리 엔드포인트 (api 서비스)
- §3.2.2: 클릭 통계 엔드포인트 (redirect 서비스)
- §2: 인증 스키마
- §6: 에러 응답 포맷 및 에러 코드 목록
