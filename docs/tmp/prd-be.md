# PRD: GoShort Backend

---

## 1. 요약

URL 단축 서비스(GoShort)의 백엔드 시스템. 두 개의 독립적인 마이크로서비스로 구성된다: 단축 URL의 CRUD를 담당하는 **api** 서비스와 단축 코드를 원본 URL로 리다이렉트하고 클릭 통계를 제공하는 **redirect** 서비스. 프론트엔드는 본 프로젝트의 범위에 포함되지 않으며, 백엔드 API만을 제공한다.

---

## 2. 문제 / 목표

### 목표
- 원본 URL을 짧은 코드로 단축하여 생성, 조회, 목록 조회, 삭제할 수 있는 REST API를 제공한다.
- 단축 코드로 접속 시 원본 URL로 HTTP 리다이렉트하며, 리다이렉트마다 클릭 횟수와 마지막 접근 시각을 추적한다.
- 두 서비스를 독립적으로 배포 가능한 MSA 구조로 설계하여, 각 서비스가 자체 책임 범위의 데이터만 소유하도록 한다.

### 비목표 (Non-Goals)
- 프론트엔드 대시보드 또는 웹 UI (별도 프로젝트로 분리)
- 사용자 회원가입/로그인 시스템 (API Key 기반 단일 테넌트 인증으로 대체)
- URL 만료(TTL) 자동 삭제 기능
- 커스텀 도메인 지원
- 클릭 통계의 시계열 분석 (일별/시간별 집계)
- A/B 테스트 또는 트래픽 분배 기능

---

## 3. 사용자 시나리오

### 시나리오 1 — 단축 URL 생성
1. API 클라이언트가 원본 URL을 포함하여 단축 URL 생성 요청을 보낸다. 선택적으로 커스텀 단축 코드를 지정할 수 있다.
2. 서버는 단축 코드를 생성(또는 커스텀 코드를 검증)하고 저장한 후, 생성된 단축 URL 정보를 응답한다.
3. 생성된 단축 URL은 즉시 리다이렉트 서비스를 통해 사용 가능하다.

### 시나리오 2 — 단축 URL로 리다이렉트
1. 브라우저 또는 HTTP 클라이언트가 단축 코드 경로로 접속한다.
2. redirect 서비스가 단축 코드에 해당하는 원본 URL을 조회하여 302 리다이렉트 응답을 반환한다.
3. 리다이렉트 시 클릭 횟수가 1 증가하고 마지막 접근 시각이 갱신된다.

### 시나리오 3 — URL 목록 조회 및 상세 확인
1. API 클라이언트가 등록된 단축 URL 목록을 페이지네이션하여 조회한다.
2. 특정 단축 코드의 상세 정보(원본 URL, 클릭 수, 생성 일시)를 조회한다.
3. 클릭 통계 엔드포인트를 통해 총 클릭 수와 마지막 접근 시각을 확인한다.

### 시나리오 4 — 단축 URL 삭제
1. API 클라이언트가 특정 단축 코드의 삭제를 요청한다.
2. api 서비스가 데이터베이스에서 레코드를 삭제하고, 캐시에서도 해당 항목을 제거한다.
3. 삭제된 단축 코드로의 리다이렉트 요청은 이후 404 응답을 반환한다.

## 4. 기능 요구사항

### 4.1 api 서비스 — URL 관리

- **FR-01**: 원본 URL을 받아 고유한 단축 코드를 자동 생성하고 저장한다. 원본 URL은 유효한 URL 형식이어야 하며 최대 2048자까지 허용한다.
- **FR-02**: 선택적으로 3~20자의 영숫자 커스텀 단축 코드를 지정할 수 있다. 이미 사용 중인 코드는 충돌 에러를 반환한다.
- **FR-03**: 생성 성공 시 단축 코드, 원본 URL, 전체 단축 URL, 생성 일시를 응답한다.
- **FR-04**: 등록된 단축 URL을 페이지네이션으로 조회할 수 있다. 기본값은 page=1, limit=20이며, limit은 1~100 범위이다.
- **FR-05**: 목록의 각 항목에는 단축 코드, 원본 URL, 단축 URL, 클릭 수, 생성 일시가 포함된다.
- **FR-06**: 단축 코드로 개별 URL의 상세 정보(코드, 원본 URL, 단축 URL, 클릭 수, 생성 일시)를 조회할 수 있다.
- **FR-07**: 단축 코드로 URL을 삭제할 수 있다. 삭제 시 데이터베이스와 캐시 양쪽에서 제거한다.
- **FR-08**: 모든 URL 관리 엔드포인트는 `X-API-Key` 헤더를 통한 API Key 인증을 요구한다. 누락되거나 유효하지 않은 키는 401 에러를 반환한다.

### 4.2 redirect 서비스 — 리다이렉트 및 통계

- **FR-09**: 단축 코드 경로로 GET 요청이 들어오면 원본 URL로 302 리다이렉트 응답을 반환한다.
- **FR-10**: 리다이렉트 처리 시마다 해당 코드의 클릭 횟수를 원자적으로 증가시키고 마지막 접근 시각을 갱신한다.
- **FR-11**: 단축 코드별 클릭 통계(총 클릭 수, 마지막 접근 시각)를 조회하는 엔드포인트를 제공한다. 이 엔드포인트는 인증 없이 접근 가능하다.
- **FR-12**: 캐시에 존재하지 않는 단축 코드로의 요청은 404 에러를 반환한다. 데이터베이스로의 폴백은 수행하지 않는다.

### 4.3 에러 처리

- **FR-13**: 모든 에러 응답은 통일된 형식(`error.code`, `error.message`)으로 반환한다.
- **FR-14**: 에러 코드로 `INVALID_URL`(잘못된 URL 형식), `INVALID_CODE`(잘못된 코드 형식), `UNAUTHORIZED`(인증 실패), `NOT_FOUND`(코드 미존재), `CODE_CONFLICT`(코드 충돌), `INTERNAL_ERROR`(서버 오류)를 사용한다.

## 5. 비기능 요구사항

### 성능
- **NFR-01**: 리다이렉트 응답 지연시간은 캐시 히트 기준 50ms 이내여야 한다.
- **NFR-02**: URL 목록 조회는 1000개 이하의 데이터셋에서 200ms 이내에 응답해야 한다.

### 가용성
- **NFR-03**: api 서비스 장애 시에도 redirect 서비스의 리다이렉트 기능은 독립적으로 동작해야 한다 (이미 캐시된 URL에 한해).
- **NFR-04**: redirect 서비스 장애 시에도 api 서비스의 CRUD 기능은 독립적으로 동작해야 한다.

### 데이터 일관성
- **NFR-05**: URL 생성 시 데이터베이스 영속화가 캐시 동기화보다 우선한다. 캐시 쓰기 실패 시에도 데이터베이스에는 저장되어야 한다.
- **NFR-06**: 클릭 횟수는 최종적 일관성(eventual consistency)을 허용한다. 정확한 실시간 집계보다 낮은 지연시간을 우선한다.

### 보안
- **NFR-07**: API Key는 환경 변수를 통해 설정하며, 소스 코드에 하드코딩하지 않는다.

## 6. 제약사항 및 리스크

| 구분 | 내용 |
|------|------|
| **서비스 간 결합** | api 서비스와 redirect 서비스는 공유 캐시 인스턴스를 통해 통신한다. api가 캐시에 쓰고 redirect가 읽는 단방향 의존 관계이므로, 캐시 인스턴스 장애 시 양쪽 서비스 모두 영향을 받는다. |
| **캐시 정합성** | 캐시 동기화는 최선 노력(best-effort) 방식이다. URL 생성 시 캐시 쓰기가 실패하면, 해당 코드는 캐시에 재적재될 때까지 리다이렉트가 불가하다. |
| **클릭 카운트 비정규화** | api 서비스의 데이터베이스에도 클릭 수가 저장되지만, 실시간 정확한 값은 redirect 서비스의 캐시에 존재한다. 두 값은 동기화되지 않는다. |
| **단일 테넌트** | 현재 API Key 기반 단일 테넌트 모델이므로, 멀티 테넌트 확장 시 인증 체계 변경이 필요하다. |

## 7. 기술 고려사항

### 서비스 아키텍처

본 프로젝트는 두 개의 독립적인 서비스로 구성된 MSA(Microservices Architecture)이다:

| 서비스 | 포트 | 책임 | 데이터 소유권 |
|--------|------|------|---------------|
| **api** | 8080 | URL 단축 CRUD, 인증, 데이터 영속화, 캐시 쓰기 | PostgreSQL `urls` 테이블, Redis `url:{code}` 키 (쓰기 전용) |
| **redirect** | 8081 | 단축 코드 리다이렉트, 클릭 통계 추적 및 조회 | Redis `url:{code}` 키 (읽기 전용), Redis `clicks:{code}` 및 `last_accessed:{code}` 키 (읽기/쓰기) |

### 서비스 간 통신

- 두 서비스 간 직접적인 HTTP/gRPC 호출은 없다.
- 공유 Redis 인스턴스를 통한 데이터 동기화: api 서비스가 URL 생성 시 캐시에 기록하고, redirect 서비스가 이를 읽어 리다이렉트를 수행한다.
- api 서비스가 URL 삭제 시 캐시에서도 해당 키를 제거한다.

### 기술 스택

- **언어**: Go 1.22+
- **프로젝트 구조**: Go 모노레포 (`go.work`)로 공유 패키지(`pkg/`) 관리
- **데이터베이스**: PostgreSQL 16 (api 서비스 전용, URL 영속 저장)
- **캐시**: Redis 7 (api 서비스가 쓰기, redirect 서비스가 읽기 및 카운터 관리)
- **컨테이너화**: Docker Compose로 전체 서비스 및 의존성 실행

### Docker Compose 구성

| 컨테이너 | 이미지 소스 | 포트 |
|-----------|-------------|------|
| api | `services/api/` 빌드 | 8080 |
| redirect | `services/redirect/` 빌드 | 8081 |
| postgres | postgres:16-alpine | 5432 |
| redis | redis:7-alpine | 6379 |
