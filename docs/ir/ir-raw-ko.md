## ANT Works: Spec-to-Branch Pipeline

### 한 줄
ANT Works는 스펙을 피처 단위 작업(브랜치)로 구조화하고, 설계부터 구현과 프리뷰까지 반복 가능한 개발 운영 흐름으로 실행한다.

### 정의
- **Spec**: PRD, 지시문, 레퍼런스 자료(가능하면 UI 스크린샷 포함).
- **Branch**: 팀이 리뷰·프리뷰·머지·롤백·추적을 수행하는 작업 단위.
- **Pipeline**: Spec을 검증 가능한 결과(프리뷰/빌드 가능한 상태)로 만드는 표준 흐름.

---

## 요약

### 제품 범주
- Idea-to-Prototype: 대화/프롬프트 중심의 빠른 결과물 생성과 반복.
- Spec-to-Branch Pipeline(ANT): 명시적 스펙을 기준으로 작업을 분해하고 팀 운영 단위로 결과를 만든다.

### 핵심 가치
- 병렬 개발 가능한 작업 단위(Branch)로 결과를 만든다.
- 프리뷰/개발서버 운영을 피처 단위로 분리한다.
- 단계별 비용/지연/품질 최적화를 위해 job/node 단위 모델 라우팅을 지원한다.

---

## 문제 정의

### 현업에서 실제로 어려운 것
- 스펙이 있어도 구현 전에 작업 단위로 분해하고 경계를 합의하는 비용이 든다.
- 결과물이 팀이 운영 가능한 단위(리뷰/머지/롤백)로 나오지 않으면, 이후 반복 개발에서 다시 병목이 생긴다.
- 프리뷰/개발서버가 피처 단위로 격리되지 않으면 병렬 개발이 어렵다.

---

## 카테고리 프레이밍

### Idea-to-Prototype
- 대화/프롬프트 중심으로 빠르게 결과물을 만들고 반복하며 다듬는다.
- 탐색과 데모에 최적화된다.

### Spec-to-Branch Pipeline (ANT)
- 명시적 스펙을 1급 입력으로 취급한다.
- 결과를 팀 운영에 적합한 피처 단위 작업 단위(Branch)로 만든다.
- 병렬 작업, 리뷰, 프리뷰, 머지, 인수인계를 전제로 최적화된다.

## 개발 운영에서 Branch

### 의미
- Branch는 Git 기능 자체가 아니다.
- Branch는 팀이 운영하는 변경 단위(작업 단위)다.
- Git 브랜치는 그 변경 단위를 담는 구현 수단이다.

### 왜 중요한가
- 공유 베이스에 막히지 않는 병렬 개발.
- 베이스 브랜치로부터의 리스크 격리.
- 변경의 리뷰 가능성과 추적 가능성.
- 머지와 롤백을 통한 통제된 통합.

### ANT에서의 구현(관찰 가능한 특징)
- 피처 생성 시 해당 피처 브랜치로 전환/생성 가능.
- 브랜치 네이밍 표준화(`feature/{featureName}`)와 정규화 처리.
- 베이스 브랜치 설정 가능(`branchBase`).
- 브랜치 전환과 동기화를 위한 upstream/remote 처리 포함.

## 개발 운영에서 Pipeline

### 의미
Pipeline은 Spec을 검증 가능한 결과로 바꾸는 반복 가능한 운영 흐름이다.

### 왜 중요한가
- Spec에서 결과까지 리드타임 단축.
- 표준 단계로 개발자/프로젝트 간 편차 감소.
- 산출물 생성과 품질 게이트를 일관되게 적용 가능.

### ANT에서의 구현(관찰 가능한 특징)
- 피처 워크스페이스 단위로 job 실행(design/code/learn).
- 피처 단위 경로 격리와 job 상태 저장.
- 멀티 패키지 프로젝트를 포함한 개발서버 운영과 프록시 접근 지원.

---

## 설계를 1급 제약으로 취급

### 주장
ANT는 보이는 결과만 맞추는 것이 아니라 팀이 이어서 개발할 수 있는 구조를 만들도록 설계된 코드를 생성한다.

### 생성 코드베이스에서 관찰되는 신호(대표 사례 기준)
- 레이어 경계(domain/application/infrastructure/presentation 패턴).
- 풀스택 구성에서 공유 계약/DTO 타입 구조.
- strict TypeScript, lint/typecheck 스크립트 포함.
- 일부 영역에서 테스트 코드 존재.

---

## 지원 작업 모드

### 신규 프로젝트 부트스트랩
- 스펙에 맞는 실행 가능한 코드베이스 스캐폴드를 만든다.
- 스택에 맞게 dev/build/typecheck/lint 스크립트를 구성한다.

### 기존 프로젝트 작업
- 기존 코드베이스에 피처 추가.
- 기존 제약을 존중한 리팩토링.
- design/code job은 코드베이스 컨텍스트(검색/리트리벌)를 사용한다.

---

## 프리뷰와 개발 환경

### 피처 단위 프리뷰
- dev server 프록시 키에 피처가 포함된다(`tenant:user:project:feature`).
- 피처별 프리뷰를 독립적으로 운영할 수 있다.

### IDE 스코프
- IDE 프록시는 프로젝트 단위로 코드베이스를 연다.
- IDE에서 보이는 코드는 브랜치 선택에 의해 결정된다.

---

## 작업별·노드별 모델 라우팅(Job/Node Optimization)

### 개념
워크플로우 단계별로 최적 모델이 다르다(비용/지연/품질).

### 구현(관찰 가능한 특징)
- job 타입(`design`, `code`, `learn`)과 node 타입(예: `decompose`, `plan`, `docGen`, `execute`, `validate`)에 따라 모델 선택 가능.
- 선택 우선순위:
  1. job+node 지정 모델
  2. job 기본 모델
  3. 환경 기본 모델
  4. 하드코딩된 폴백

## Proof / Traction (초기 단계, 사실 기반)

### 내부 검증 방식(현재까지)
- 서로 다른 유형의 프로젝트에서 “생성 결과의 구조”를 점검했다:
  - 프론트(외부 API 소비)
  - 풀스택 모노레포(프론트+백엔드 분리)
  - 스크린샷 기반 랜딩/SSR(스펙 준수 중심)

### 관찰된 결과 신호
- 실행 스크립트와 타입체크/린트 구성이 포함된 프로젝트가 생성됨.
- 레이어/경계 패턴과 계약 타입이 결과물에 반영됨.
- 피처 브랜치 단위로 작업이 분리되어 운영 가능함.

## ICP / Buyer

### ICP(이 제품이 맞는 팀)
- 스펙(PRD/디자인)이 존재하고, 피처를 반복적으로 병렬 개발하는 팀.
- PR 리뷰/브랜치 운영 문화가 있고 프리뷰가 중요한 팀.
- 내부 표준화/온보딩 비용이 문제인 조직.

### Buyer(구매 판단 라인)
- Engineering/Platform/DevEx 책임자 라인.

## 비즈니스 모델(가설)

## 리스크와 평가 질문

### 산출물 품질 편차
- 질문: 생성된 변경이 큰 재작성 없이 리뷰를 통과하는가?
- 지표: 리뷰 왕복 횟수, 리그레션/핫픽스 빈도.

### 비용 구조
- 질문: job/node 단위로 실행 비용을 통제할 수 있는가?
- 지표: 작업 단위 평균 실행시간/모델 비용, 재실행률.

### 도입
- 질문: 기존 Git 기반 운영에 자연스럽게 결합되는가?
- 지표: 온보딩 시간, 반복 사용률, 피처의 time-to-preview.
