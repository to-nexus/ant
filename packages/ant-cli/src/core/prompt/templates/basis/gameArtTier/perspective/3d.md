## Art Perspective: 3D

**Activation gate**: `gameArtTier.perspective === '3d'`.

3D is realized by layering the **enable3d** extension (three.js render + ammo.js physics) onto the
same Phaser host. The engine stays `phaser`; enable3d supplies the third dimension. The whole
in-canvas world is built from **code-only built-in primitives** — no imported model assets.

### Engine bridge

- A 3D scene extends enable3d's `Scene3D` (a `Phaser.Scene` subclass), so every scene-lifecycle,
  event, viewport, and React-HUD rule from the Phaser engine partial still holds unchanged.
- `this.accessThirdDimension()` (in `init`/`create`) exposes `this.third` — the three.js scene,
  camera, lights, and primitive factory. Depend on the `enable3d` package (the self-contained
  dependency rule installs it, exactly as with Phaser itself).

### Camera

- A perspective camera with an explicit position looking at the scene origin is the default; an
  orthographic camera is the deliberate choice for a flat / isometric-feel 3D look.
- The camera MUST be positioned — an unplaced camera sees nothing. State the viewpoint (orbiting,
  chase, first-person, fixed) as a single committed choice, mirroring how a 2D project commits one
  sub-view.

### Depth

- Depth is a real z-buffer — objects occlude by world position, not by a committed layer index.
  Do NOT reintroduce manual render-layer sorting; that is a 2D idiom.

### Built-in primitives (code-only, no assets)

Every world object is a primitive created in code and colored from the concept palette — never an
imported mesh in this scope:

- Non-physics: `this.third.add.box(...)` / `.sphere(...)` / `.ground(...)` / `.cylinder(...)` /
  `.cone(...)` / `.torus(...)`.
- With physics (when the game needs collisions/gravity): `this.third.physics.add.box(...)` etc.
- Materials carry color from the concept palette (`{ lambert: { color } }` / standard material).
  A scene with no light renders black — commit at least an ambient + a directional light (or the
  `this.third.warpSpeed(...)` scaffold, which adds ground / light / camera defaults).

### Input ↔ camera mapping

- Map input to world axes relative to the camera, not to screen pixels. State the control model
  (orbit / first-person / fixed-camera translate) explicitly — camera-relative input is the #1 3D
  UX trap, the direct analogue of 2D isometric input confusion.

### Asset implications

- Geometry is code; the palette drives color. A pure-primitive 3D game needs few or no
  `game-art-assets.json` entries.
- Imported 3D models (`.glb` / `.gltf`) are out of scope here — they re-enter via the external-asset
  path in a later phase. Do NOT reach for a model loader; build from primitives.

### Blind-spot reminders

- ⚠️ **No light = black screen.** The most common "nothing renders" 3D bug. Always add a light (or `warpSpeed`).
- ⚠️ **Unpositioned camera** sees nothing — set position and look-at before expecting output.
- ⚠️ **Physics vs non-physics** primitives are different factories — a `this.third.add.*` box has no
  body and will not collide. Pick the factory that matches whether the object needs physics.
- ⚠️ **Dispose on shutdown** — three.js geometries/materials created in a scene MUST be released in
  `shutdown`, in addition to the Phaser listener cleanup, or repeated scene restarts leak GPU memory.
