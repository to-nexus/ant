## Art Perspective: 2D

**Activation gate**: `gameArtTier.perspective === '2d'`.

### Camera

The 2D camera fits one of four sub-views; the project commits one explicitly:

| Sub-view | Description |
|---|---|
| **2D side** | Camera looks at the world from the side. Y is "up". Used for platformers, side-scrolling shooters, fighting games. |
| **2D top-down** | Camera looks straight down. Y is "north" (or screen-up). Used for arena shooters, strategy, top-down RPGs. |
| **2D isometric** | Camera angled at ~30° / 45° to fake depth. Tiles are rhombus-shaped. Used for tactics RPGs, builders. |
| **2D screen-space** | Camera fixed to screen coordinates (puzzles, UI-heavy games). No world camera at all. |

A 2D project that mixes sub-views (top-down world + side-view battle) MUST state the transition explicitly.

### Depth handling

- **Z-ordering** by render layer. The catalog commits layer indices (background, midground, entities, foreground, UI). No depth buffer.
- **Parallax** (optional) — multiple background layers move at different rates to fake distance. Parallax is a 2D-side / 2D-top idiom; iso uses it rarely.
- **Sorting strategy** — `2D top-down` and `2D iso` typically Y-sort entities (lower Y = drawn first / behind); `2D side` sorts by explicit layer.

### Input ↔ camera mapping

| Sub-view | Typical input mapping |
|---|---|
| 2D side | Left/right = horizontal world axis; up = jump or aim; down = crouch or stash. |
| 2D top-down | All four cardinals = world translation. WASD or twin-stick. |
| 2D isometric | Cardinals map to world axes ROTATED 45° (W = up-right, A = up-left). Players need indication or camera-relative mapping. |
| 2D screen-space | Tap / drag is direct (no world axis). |

Iso input mapping is the most common UX trap — explicit indication or camera-relative mapping is mandatory.

### Asset implications

- Sprites are flat — no z-component. Frame count drives motion fluidity.
- Iso sprites need facing variants (typically 4 or 8 directions).
- Tilemaps fit naturally — `assets/game/tilemaps/` is a 2D-only category.
- Under the 2D perspective, 3D models are out of scope — if the catalog references `.glb` / `.gltf`, that is a category mismatch. Choose the 3D perspective for mesh-based worlds.

### Render primitives (2D)

Scenes extend `Phaser.Scene` (a 2D camera; no `Scene3D`). Baseline visual scope
(`_meta.visualScope === 'baseline'`, the default) draws world objects with procedural
`Phaser.GameObjects.Graphics`:

```ts
const g = this.add.graphics();
g.fillStyle(0xff5577, 1);            // ARGB (alpha 0..1)
g.fillRect(x, y, width, height);
g.lineStyle(2, 0xffffff, 0.8);
g.strokeCircle(cx, cy, r);
```

Allowed in baseline visual scope: `fillStyle` / `fillRect` / `fillCircle` / `fillTriangle` /
`fillRoundedRect`, `lineStyle` / `strokeRect` / `strokeCircle` / `strokeRoundedRect`,
`Phaser.GameObjects.Text` for glyphs, and `Phaser.GameObjects.Sprite` only when an `external`
catalog entry exists (preloaded in `BootScene`). Atlas-enabled hook (`_meta.visualScope ===
'atlas-enabled'`) adds `this.load.atlas` / `this.load.spritesheet`, `this.add.particles` with custom
textures, and WebGL shader pipelines. Do NOT reach for `Phaser.GameObjects.Image` with a remote URL —
assets come through the `assets/game/...` pool (I6).

### Code-time consequences

- `setOrigin(0.5, 1)` on entities for foot-anchored Y-sort in top-down / iso.
- Tilemap loaders (`this.load.tilemapTiledJSON`) are 2D-only.
- Particle emitters render at z-layer of their parent; parallax layers MUST live in distinct cameras or sub-containers.

### Blind-spot reminders

- ⚠️ **Sub-view mixing** without an explicit transition rule is the #1 player-confusion bug.
- ⚠️ **Iso input mapping** decided at coding time often diverges from designer intent — commit early in the PRD.
- ⚠️ **Y-sort ties** (two entities at the same Y) need a deterministic tiebreaker (entity id, spawn order). Random sort flickers.
